## Context

渠道监控已经可以直接向外部地址发起探测，也可以把地址设置为当前服务地址。后一种情况下，请求会再次进入 API Key 网关并由调度器选择账号；当前系统没有一个可靠的请求级标记来区分这类探测和普通 API Key 请求。

本变更需要跨越监控配置、监控 HTTP 客户端、认证/网关生命周期、账号调度、Redis 状态和管理端设置。要求保持实现简单：冷却不再按模型或错误族分支，只处理带监控标记的请求，并将所有失败合并为一个账号级状态。

## Goals / Non-Goals

**Goals:**

- 持久化 `use_current_service`，只有用户点击“使用当前服务”并保存后才标记监控。
- 为标记请求建立可验证的内部上下文，并在所有网关协议的账号尝试完成时统一观察结果。
- 使用账号级、跨分组共享的五档冷却阶梯，支持 Redis 并发合并、到期升级和成功清理。
- 根据探测实际耗时临时增加账号有效优先级，支持正常响应立即恢复和自动超时恢复。
- 提供版本化配置、严格校验、运行时刷新和恢复默认值接口及页面操作。

**Non-Goals:**

- 不改变普通 API Key 请求、OAuth、Setup Token、API Key 号池或其他账号类型的既有错误处理。
- 不按模型、平台、故障类型或 API Key 类型建立新的冷却维度。
- 不新增冷却历史、告警、审批或永久凭据错误处理。
- 不把手工填写相同域名视为“使用当前服务”，也不通过 endpoint 字符串推断开关。

## Decisions

### 1. 用持久化开关而不是地址推断

在 `channel_monitors` 增加 `use_current_service` 布尔字段，默认 `false`。管理端按钮同时设置 endpoint 和该字段；编辑表单保留服务端字段，用户手工修改 endpoint 时清除该字段，必须再次点击按钮才能开启。这样不会因为域名、反向代理或部署地址变化误触发冷却。

### 2. 使用内部签名监控标记

监控 checker 在 `use_current_service=true` 时为每个 HTTP 请求增加内部 header，内容包含 monitor ID、随机请求 ID、签发时间和签名。签名使用服务已有的安全密钥，网关中间件只接受未过期且签名正确的标记，并将解析后的结构写入 request context；外部客户端伪造普通 header 不能开启冷却。直连外部 endpoint 的监控不带标记。

### 3. 在统一账号尝试出口观察结果

新增轻量 `ChannelMonitorProbeObserver`，由网关服务在选定账号的请求开始、成功、失败和客户端/上游取消处调用。observer 只在 context 含有效监控标记时工作，接收账号 ID、开始时间、最终状态和错误；普通请求快速返回。探测的任意失败都归入同一个 `channel-monitor` 账号键，成功清理该账号的冷却计数。安全重试仍由现有网关决定，但每个带标记的账号尝试都要有一次终态观察。

### 4. Redis 只维护账号级冷却事件

使用 `channel_monitor:cooldown:account:<id>` 保存活动截止时间、阶梯序号和事件代次。Lua 原子操作在无活动事件时把序号推进一档并设置 TTL；活动期间的并发失败只返回现有截止时间，不重复推进；到期后的下一次失败再推进。序号达到第五档后保持第五档。成功按事件代次清理，迟到的旧成功不能删除更新的事件。Redis 不可用时记录诊断日志并跳过新增冷却，不能阻塞原始请求。

### 5. 账号优先级采用“基准值 + 临时加成”

不直接覆盖数据库中的 `accounts.priority`。在 `account.extra` 的保留命名空间保存 `channel_monitor_priority`：`boost`、`increases`、`first_increased_at`。仓储使用事务/行锁或条件更新保证并发下最多增加配置次数，并在变更后同步调度快照；调度排序使用基准优先级加当前 boost。管理员修改基准优先级不会丢失临时状态。

每次带标记探测完成后按真实耗时处理：超过阈值且未到上限时 `boost += increment`、`increases += 1`；第一次增加时写入起始时间，后续增加不重置计时。耗时不超过阈值立即清零；读取或写入时若已超过自动恢复时长也先清零，再把当前超时视为新的第一次增加。

### 6. 统一配置契约和恢复默认

系统设置保存一个版本化对象：

```json
{
  "version": 1,
  "cooldown_minutes": [2, 5, 30, 60, 120],
  "slow_response_threshold_seconds": 12,
  "priority_increment": 1,
  "max_priority_increase": 3,
  "priority_auto_recovery_seconds": 3600
}
```

后端校验阶梯必须正好五个、严格递增且为正整数；其余字段按安全上下限校验。GET/PUT 返回规范化配置，`POST /admin/settings/channel-monitor-cooldown/reset` 写入并返回内置默认值。运行时缓存最近一次有效配置，读取失败时使用缓存或默认值；配置更新不需要重启。

### 7. 迁移与兼容

新增一条数据库迁移为已有监控填充 `use_current_service=false`。旧监控因此不会突然进入冷却。删除或回滚迁移前先停止使用该字段的应用版本；应用回滚时忽略未知设置键即可，Redis 键自然过期，不影响普通请求。

## Risks / Trade-offs

- [内部 header 被错误转发到外部上游] -> 只在发往当前服务地址时设置，并在网关入口消费后从转发 header 中移除；签名和过期时间限制伪造窗口。
- [Redis 短暂不可用导致账号继续被探测] -> 冷却状态写入失败只降级为不新增状态，记录指标和日志；请求本身不因 Redis 阻塞。
- [并发慢响应同时更新优先级] -> 使用数据库原子条件更新/行锁和调度缓存同步，测试高并发下 boost 不超过上限。
- [管理员保存非法阶梯导致运行时异常] -> PUT 在服务端拒绝非法结构，前端在提交前做同样校验，运行时永不直接使用未规范化数据。
- [探测跨实例经过不同服务节点] -> 签名密钥来自共享安全配置，标记只依赖 monitor ID 和时间，不依赖进程本地状态。

## Migration Plan

1. 发布数据库迁移，增加 `use_current_service` 并为历史行填充 `false`。
2. 发布后端设置 API、标记解析、冷却 observer 和优先级状态处理；默认配置立即可用。
3. 发布管理端开关和配置页面，管理员按需点击“使用当前服务”并保存。
4. 回滚时先关闭监控开关，再回滚应用；保留字段和设置数据不会改变普通请求，Redis 状态等待 TTL 到期。

## Open Questions

无。默认阶梯、阈值、增量、最大增加次数和自动恢复时长均已由需求确定，并允许通过配置覆盖。
