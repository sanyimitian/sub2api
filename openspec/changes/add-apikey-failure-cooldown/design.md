## Context

账号调度已经能够排除 `rate_limit_reset_at`、`overload_until`、`temp_unschedulable_until` 及 `extra.model_rate_limits` 中仍有效的状态，账号仓储写入也会同步调度快照并发布账号变更事件。但是，上游失败的分类与状态写入分散在 `RateLimitService`、OpenAI/Grok 专用网关、Anthropic/Gemini/Antigravity 转发和传输错误处理路径中：

- 429 与 529 有独立设置和账号级字段；
- 模型不存在使用 `model_rate_limits`；
- OpenAI 非池模式 API Key 的部分 5xx 只使用进程内“账号＋模型”短暂避让；
- 传输、401、403 和自定义临时不可调度规则分别维护自己的计数或固定冷却；
- 池模式刻意跳过大部分默认账号状态处理。

本变更只统一 `type=apikey` 且非池模式账号的可恢复故障冷却。账号可能绑定多个分组，因此账号级冷却必须以账号为全局作用域；模型级冷却必须以“账号＋最终上游模型”为全局作用域。系统部署可能包含多个服务实例，并可能在一个冷却写入传播前已有大量并发请求在途。

## Goals / Non-Goals

**Goals:**

- 建立 API Key 可恢复故障的唯一冷却决策入口，统一分类、连续失败、阶梯、持久化和成功重置。
- 复用现有账号级和模型级调度状态，不新增数据库表或账号字段。
- 通过共享原子状态把一个活跃冷却窗口内的并发失败合并为同一冷却事件。
- 通过发送前共享守卫缩短调度快照传播期间继续撞击故障账号的窗口。
- 保持现有安全重放边界、账号自定义规则优先级和非目标账号类型行为。
- 允许管理员在运行时配置每个故障族的启用状态、冷却阶梯和阶梯模式。
- 对每个受管账号尝试统一执行 29 秒首个有效内容期限，避免无响应连接长期占用账号与请求资源。

**Non-Goals:**

- 不改变池模式、OAuth、Setup Token、Bedrock 或其他非 API Key 账号的故障策略。
- 不新增无效 Key、令牌撤销或永久账号错误的识别、告警、恢复或生命周期管理。
- 不建立上游平台或分组级共享熔断；明确全局故障只冷却实际失败账号。
- 不新增冷却历史、审计表、人工审批、短信或 Webhook 通知。
- 不改变请求参数错误、内容安全拒绝、客户端取消和客户端自身超时的既有响应语义。

## Decisions

### 1. 使用统一协调器而不是继续扩展状态码分支

新增 `APIKeyCooldownCoordinator`，每个上游账号尝试通过统一的 `ObserveFailure` 或 `ObserveSuccess` 出口报告结果。协调器只处理 `AccountTypeAPIKey` 且 `!account.IsPoolMode()` 的账号，并由以下职责组成：

- `FailureClassifier`：把 HTTP 响应、上游传输错误和请求生命周期归一化为稳定故障族；
- `CooldownPolicyProvider`：提供经校验的版本化运行时配置；
- `FailureEpisodeStore`：原子维护冷却事件、连续失败次数和共享冷却截止时间；
- `CooldownStateWriter`：把决策写入现有账号级或模型级持久状态；
- `CooldownGuard`：在真正发送上游请求前执行共享冷却最终检查。

协调器返回结构化决策，但不向客户端写响应，也不直接执行账号切换。现有 failover 循环继续拥有重试、失败账号集合、切换预算和响应终止权。

替代方案是分别修改 429、529、5xx 和各平台传输分支。该方案改动表面较小，但会复制计数、配置、并发合并和成功重置逻辑，因此不采用。另一个替代方案是新增通用冷却表；它能保留多个并行原因和历史，但需要迁移、查询、快照与缓存模型改造，超出当前需求。

### 2. 使用结构化尝试观察值并保证一次尝试只决策一次

`FailureObservation` 至少携带：

- 唯一尝试 ID、尝试开始时间和发送前守卫返回的冷却事件代次；
- 账号 ID、账号类型、池模式、平台和最终规范化上游模型；
- HTTP 状态、允许读取的响应头、受限且脱敏的结构化错误摘要；
- 传输错误类别、请求是否已发送、客户端是否取消或超时、响应是否已经开始下发。

同一上游尝试在多个旧错误出口中被观察时，协调器按尝试 ID 去重。接入点必须位于账号尝试的终态边界；已有 429 配额快照解析、错误响应映射等附加逻辑仍可运行，但 API Key 冷却写入必须只来自协调器。

### 3. 固定分类优先级，管理员规则只有实际命中时才消费错误

分类按以下顺序执行：

1. 不适用的账号类型或池模式直接返回不处理；
2. 账号自定义错误码或临时不可调度规则实际命中时，交给现有逻辑并停止默认冷却判断；
3. 参数错误、内容安全拒绝、客户端取消、客户端自身超时及已开始下发响应等明确请求级错误返回不处理；
4. 明确无效 Key、令牌撤销或现有永久错误信号交给现有错误处理，协调器不冷却；
5. 匹配已知可恢复故障族；
6. 仍无法分类的上游故障进入账号级循环兜底。

账号仅启用自定义规则但本次没有任何规则命中时，必须继续进入系统默认分类，不能形成“开启后未命中即跳过所有处理”的空档。

### 4. 故障族、作用域与默认策略集中配置

新增版本化 `api_key_failure_cooldown_settings` 系统设置。每个故障族包含 `enabled`、正整数秒数组 `cooldowns` 和 `mode`；`mode` 仅接受保持末档或循环阶梯。作用域是故障语义的一部分，不允许通过管理界面改写。

| 故障族 | 作用域 | 默认阶梯 | 默认模式 |
|---|---|---:|---|
| 429 且有可靠上游时间 | 账号 | 到上游时间 | 上游时间优先 |
| 429 无重置时间 | 账号 | 60、300、900 秒 | 保持末档 |
| 529 或明确模型过载 | 账号＋模型；无模型或明确整号时为账号 | 60、300 秒 | 保持末档 |
| 500/502/503/504、上游连接超时、连接重置、空响应 | 账号 | 30、120、600 秒 | 保持末档 |
| 明确临时并发或临时访问限制 403 | 账号 | 300 秒 | 保持末档 |
| 明确账号被封或永久权限失效 | 账号 | 300 秒 | 保持末档 |
| 未明确为无效 Key 的其他 401 | 账号 | 1800 秒 | 保持末档 |
| 配额或余额耗尽 | 账号 | 3600 秒 | 保持末档 |
| 模型不存在或账号不支持模型 | 账号＋模型 | 1800 秒 | 保持末档 |
| 明确全局故障 | 当前失败账号 | 1800 秒 | 保持末档 |
| 无法分类的上游故障 | 账号 | 60、600、1800 秒 | 循环阶梯 |

可靠 `Retry-After` 或供应商重置时间必须优先于本地阶梯；无效、已过期或不可解析的时间回退到对应本地策略。配置读取失败时优先使用最近一次有效配置，从未成功读取时使用内置默认值。非法配置在写入 API 处拒绝。

### 5. 以冷却事件而不是请求数量计算连续失败

`FailureEpisodeStore` 使用版本化 Redis 键，并通过单个原子脚本维护作用域状态。账号级键由账号与故障族组成；模型级键由账号、规范化模型与故障族组成，不包含分组。

原子失败转换规则：

1. 当前作用域没有活跃冷却时，连续失败次数增加一次，创建新事件代次，按次数计算阶梯并写入共享截止时间；
2. 当前作用域仍处于活跃冷却时，后续失败合并到当前事件，不增加次数、不缩短截止时间；
3. 保持末档策略使用 `min(streak-1, len(cooldowns)-1)`；循环策略使用 `(streak-1) mod len(cooldowns)`；
4. 只有创建新事件的调用负责首次持久化；若持久化失败，事件状态允许一个后续调用有限重试持久化，但不重复计数。

发送前守卫返回当前事件代次作为尝试令牌。成功转换只在以下条件全部满足时清除连续失败状态：冷却已经到期、成功尝试不是冷却创建前已在途的旧尝试、尝试令牌与当前事件代次一致。任何有效成功响应都清除账号的账号级故障计数及当前规范化模型的模型级故障计数，但不提前缩短已持久化冷却。

### 6. 复用现有持久状态并强化单调写入

账号级新冷却统一写入 `temp_unschedulable_until` 与结构化 `temp_unschedulable_reason`。现有 `SetTempUnschedulable` 已按“新截止时间更晚才更新”执行，并会发布账号变更事件、同步调度快照，因此账号在所有关联分组中被排除。

模型级冷却写入 `extra.model_rate_limits[normalized_model]`。仓储必须提供原子“只延长、不缩短”更新：只有新截止时间晚于当前有效截止时间时才替换，同时保留结构化故障族和冷却事件信息。最终模型键沿用各平台已有模型映射和规范化逻辑，避免客户端别名绕过冷却。

到期状态由现有 `IsSchedulable` 和模型限流检查自动忽略，无需后台解除任务。已有过期模型条目通过后续更新或管理端清理惰性移除。

### 7. 使用共享发送前守卫缩短快照传播竞态

调度快照仍是主要候选来源。账号被选中并通过现有本地检查后、真正发送上游请求前，`CooldownGuard` 对选中账号及规范化模型检查共享事件状态：

- 命中活跃账号级或模型级冷却时，把账号加入当前请求排除集合并重新选择；
- 未命中时返回事件代次并允许发送；
- 共享缓存不可用时回退到现有账号快照和最终新鲜度检查，不让缓存故障阻断全部流量。

守卫不能撤回冷却创建前已经发送的请求；这些在途结果仍会被事件合并吸收。该设计避免为每个候选逐一访问 Redis，只在最终候选发送前执行有界检查。

### 8. 保持故障转移与重放安全边界

冷却决策成功后，当前请求立即排除该账号。只有现有调用链判定安全可重放时才切换到同组下一个候选。客户端取消、客户端自身超时、响应已经开始下发或插件明确表示请求已发送且不能安全重放时，不因冷却新增重放。

分类器必须区分客户端截止时间与上游连接、读取或首输出超时：前者不冷却，后者属于可恢复上游故障。

### 9. 保持非目标逻辑与配置兼容

- 池模式继续使用现有同账号重试和可选 OpenAI 池 API Key 健康熔断；
- 非 API Key 账号继续使用现有 429、529、401、403 和传输错误逻辑；
- 原有 429/529 设置接口继续服务未纳入协调器的账号，不隐式映射到新阶梯；
- 现有冷却字段保持有效并自然到期；
- 对 API Key 非池模式账号，旧的 OpenAI 账号＋模型 5xx 进程内避让由新账号级策略替代，避免双重处罚；
- 现有管理端恢复操作继续清除账号的全部可恢复状态和相关共享事件。

### 10. 以尝试级首个有效内容守卫覆盖全部 HTTP 转发协议

每个适用账号在发送前守卫放行后创建一个固定 29 秒的 `FirstValidContentGuard`。守卫绑定账号尝试而非整个客户端请求，并可同时取消普通上游上下文与为了流式排水而分离客户端取消信号的上游上下文。以下事件解除守卫：

- 非流式响应向下游写入首个非空应用响应体；
- 流式响应向下游写入首个非空且不是 SSE 注释/保活的应用帧；
- WebSocket turn 向下游转发首个上游应用帧；
- 尝试以有效成功终态完成。

仅写入 HTTP 响应头、调用 Flush、空白 body 或 SSE 注释保活不解除守卫。期限到达时，守卫取消当前账号的上游尝试并产生强类型 `first_valid_content_timeout` 结果；失败观察必须将其归入账号级 `transient_upstream`，即使下游此前只收到响应头或保活，也允许创建冷却，但不得据此扩大安全重放范围。

现有 failover 循环继续决定原始请求的结局：安全可重放且存在候选时排除冷却账号并重选，否则尽快返回 504。渠道监控以“当前服务＋我的 Key”调用本服务时是普通网关流量，不豁免此期限；其响应头等待上限调整为 35 秒，使首个 29 秒超时有时间完成冷却与错误响应。

## Risks / Trade-offs

- [风险] 冷却创建前已有大量请求发送，上游仍会收到一次不可避免的并发突发。→ [缓解] 事件合并防止计数膨胀，发送前共享守卫阻止冷却后的新流量。
- [风险] 多个旧错误出口对同一尝试重复上报。→ [缓解] 使用尝试 ID 去重，并把协调器接在账号尝试终态边界。
- [风险] Redis 不可用时无法跨实例合并或升级阶梯。→ [缓解] 当前请求仍按第一档持久化冷却，调度继续依赖数据库状态和快照。
- [风险] 数据库写入失败导致管理界面与共享守卫状态暂时不一致。→ [缓解] 共享事件继续阻断发送，并允许不增加计数的有限持久化重试。
- [风险] 错误正文关键词误判造成错误冷却。→ [缓解] 优先稳定错误码和结构化字段，限制正文长度并使用严格供应商模式，不能可靠判断时只进入可恢复兜底。
- [风险] 发送前增加共享缓存访问。→ [缓解] 只检查最终候选、使用版本化短键并保留快照回退，不扫描候选池。
- [风险] 流式保活或响应头被误当成有效内容，使失效账号逃过超时冷却。→ [缓解] 尝试生命周期分别记录“响应已开始”和“有效内容已开始”，只有后者解除 29 秒守卫。
- [风险] 当前账号在第 29 秒超时后继续故障转移，调用方自身期限可能先到。→ [缓解] 只保证及时取消失败账号尝试并创建冷却；原请求仍服从调用方期限，渠道监控在 35 秒仍无最终响应时明确记录错误。
- [权衡] 不新增通用冷却表，无法同时展示多个冷却原因或历史。→ 当前需求只要求有效截止时间与调度避让，现有字段足够；未来需要治理历史时再独立设计。

## Migration Plan

1. 增加新配置模型、校验、管理 API 和前端配置区；新配置缺失时返回确认的默认值。
2. 增加共享事件存储、原子脚本、协调器和状态写入器，先以内部接口和单元测试固定语义。
3. 增加模型级单调写入和发送前守卫，并完成 PostgreSQL/Redis 集成测试。
4. 将 API Key 非池模式账号的各协议成功与失败终态接入协调器；保留非目标账号原路径。
5. 移除或旁路 API Key 非池模式账号上会重复处罚的旧冷却写入，保留配额快照、错误映射等附加职责。
6. 运行策略、并发、仓储、调度、故障转移、前端、API 契约及竞态回归测试后滚动部署。

回滚时可停止调用新协调器和发送前守卫；新设置和 Redis 键可安全保留，旧版本会忽略它们。数据库未变更，已经写入的现有冷却字段继续按截止时间自然到期。
