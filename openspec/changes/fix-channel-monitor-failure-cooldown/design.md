## Context

启用“使用当前服务”的渠道监控会携带已签名的内部监控标记进入网关。当前网关在账号尝试结束时直接把“没有网关错误”当作成功，因此 HTTP 2xx 之后由 checker 判定的挑战失败、空响应等结果无法回写冷却链；换号时，前序失败账号的结果也可能在最终结果生成前丢失。

现有 Redis 冷却存储已经提供账号级键、五档阶梯、并发合并和生成代次保护；本变更只调整监控请求的失败归因和调用时机，不改变这些冷却规则、慢响应优先级规则或管理端设置契约。

## Goals / Non-Goals

**Goals:**

- 以每个主模型或附加模型的最终 `CheckResult.status` 作为请求级失败判定，`failed` 和 `error` 必须触发归因。
- 记录一次带监控标记的模型请求实际选中的所有账号，并保留每次账号尝试的传输终态。
- 失败时冷却所有实际尝试过的普通 API Key 账号；前序失败账号即使后续换号成功也不能丢失。
- 只允许 `AccountTypeAPIKey` 且非号池账号进入本能力；没有实际选中账号时不创建归因。
- 在多实例部署中用 Redis 共享请求账本并保证重复回调、并发完成和重试幂等。
- Redis 不可用时让本次请求完全跳过冷却处理，不使用进程内替代状态，不暂停监控或阻塞原始请求，并留下诊断信号。

**Non-Goals:**

- 不修改普通 API Key 请求、OAuth、Setup Token、Service Account、API Key 号池或其他账号类型的既有调度和错误处理。
- 不改变网关重试边界、请求格式、响应语义、渠道监控配置项或慢响应优先级算法。
- 不改变现有五档冷却时长、跨分组共享、成功清理连续失败计数和已生效冷却不可提前缩短的规则。
- 不为历史监控结果补写冷却，也不迁移已有 Redis 冷却键。

## Decisions

### 1. 使用“监控请求账本”连接网关与 checker

每个带监控标记的模型请求使用标记中的 `request_id` 作为账本身份；主模型和附加模型必须生成不同的 `request_id`。网关在账号真正选中后登记一次尝试，在该账号转发终态到达时更新为 `transport_failed`、`transport_succeeded` 或 `transport_unknown`。登记内容至少包含账号 ID、是否为目标 API Key、尝试终态和请求完成状态，账本设置短 TTL，避免未完成请求永久占用 Redis。

checker 完成 `runCheckForModel` 后调用一次最终归因器，传入同一个 `request_id` 和最终状态。归因器读取并锁定账本：

- 最终状态为 `failed` 或 `error` 时，对账本中所有实际尝试过且符合目标类型的账号调用一次 `ObserveFailure`。
- 最终状态不是 `failed/error` 时，只对网关传输已失败的账号调用 `ObserveFailure`；传输成功的账号才允许按其观测到的冷却代次执行成功清理，未知终态不主动清理。
- 账本已完成最终归因后，重复回调直接返回，不重复推进阶梯；冷却存储自身的生成代次保护继续阻止迟到成功删除更新事件。

这使“最终 checker 失败”覆盖 2xx 后挑战失败、响应为空等路径，同时保留网关已经明确失败的前序账号。

### 2. 保留现有网关钩子，但将成功处理延后到最终归因

`GatewayService`、`OpenAIGatewayService` 及各协议 handler 继续在账号选中和转发结束处调用统一 observer，避免为 Chat Completions、Responses、流式和其他协议各自复制归因逻辑。observer 的职责改为：

1. 校验 context 中的可信监控标记和目标账号类型；普通请求快速旁路。
2. 将尝试及传输终态写入请求账本。
3. 传输错误可立即写入冷却，作为 checker 最终归因前的保护；传输成功不立即清理冷却，等待最终 `CheckResult` 决定。

checker 归因器使用账本中保存的幂等状态补齐或确认冷却。这样即使网关成功返回 2xx，最终 checker 失败仍会为该次请求实际选中的账号补写冷却。

### 3. 目标账号判定集中在 observer

目标资格固定为 `AccountTypeAPIKey` 且 `!account.IsPoolMode()`。OAuth、Setup Token、Service Account、号池账号以及没有账号的直连探测不写入账本，也不调用冷却存储。资格判断不依赖 endpoint、模型、分组或错误文本，避免同一账号在不同分组中产生不同冷却键；冷却仍沿用现有 `channel_monitor:cooldown:account:<account_id>`。

### 4. Redis 账本和冷却写入采用请求级不可用标记

请求账本使用 Redis 共享，逻辑上包含“尝试集合”“各尝试终态”“最终归因状态”和版本/代次字段。首次发现 Redis 连接、脚本或读写失败时，observer 将该请求标记为 `cooldown_disabled`，后续该请求不再尝试任何冷却写入；不以进程内 map 代替 Redis，也不因为写入失败暂停 checker。账本和冷却操作均使用独立的短超时上下文或异步 best-effort 写入，不能延长原始网关响应；所有失败通过结构化日志和计数指标记录请求 ID、监控 ID及错误阶段，不记录 API Key 内容。

### 5. 最终状态只认 `failed/error`

最终归因器不重新解释 HTTP 状态码、错误族或响应内容。只有 `CheckResult.status == failed` 或 `CheckResult.status == error` 才把本次实际尝试账号全部视为需要冷却；`operational`、`degraded` 等其他状态不触发全量冷却。最终状态成功时，仍遵循现有生成代次规则清理可安全清理的账号状态，不能提前缩短活动冷却。

### 6. 兼容旧标记和未完成请求

缺失、伪造或过期的监控标记继续按普通请求处理；没有 `request_id` 的旧上下文不尝试猜测账号归属，也不创建新账本。账本 TTL 到期或进程在最终归因前退出时，不做跨请求补偿，避免把后续普通请求错误归因到旧监控。已有冷却键、管理端账号状态投影和配置读取保持兼容。

### 7. 备选方案及取舍

- **只在 checker 结束时读取当前账号**：实现改动小，但换号后无法找回前序失败账号，且并发重试会丢失归因，未采用。
- **继续在网关 observer 中以 HTTP 错误直接判定全部结果**：能处理传输错误，但无法覆盖 2xx 后最终 `failed/error`，正是当前缺陷，未采用。
- **把所有尝试状态放进进程内内存并在 checker 回调时读取**：跨实例和重启会丢失，Redis 不可用时还会产生与需求相反的隐式兜底，未采用。

## Risks / Trade-offs

- [Redis 在尝试登记和最终归因之间短暂不可用，导致本次请求不产生冷却] -> 按明确降级约束放弃该请求的全部冷却，记录可检索日志/指标；后续请求仍可继续工作。
- [最终归因与网关传输终态并发到达] -> 以 Redis Lua/CAS 或等价原子更新锁定账本版本，终态更新和最终归因均幂等。
- [账本 TTL 过短导致慢请求归因缺失] -> TTL 至少覆盖监控标记有效期、网关客户端超时和最终归因缓冲，并在写入/完成时续期；仍以有限 TTL 防止泄漏。
- [异步冷却写入在进程退出前未完成] -> 仅把冷却作为 best-effort 旁路能力，保留结构化失败指标；不牺牲原始请求的返回时序。
- [最终失败会将同一请求中传输成功的账号也冷却] -> 这是已确认的归因规则：只要账号被该失败监控请求实际选中，就纳入本次失败冷却；普通请求和非目标账号仍完全旁路。

## Migration Plan

1. 先发布只读/兼容版本，确保所有“使用当前服务”请求继续生成包含独立 `request_id` 的签名标记，并确认 Redis 客户端可用性指标。
2. 发布账本 observer 和 checker 最终归因逻辑；新账本键使用独立前缀并设置 TTL，不修改已有账号冷却键格式。
3. 逐步启用回归测试和运行时指标，观察最终 `failed/error` 与账号冷却写入数量是否一致，再扩大监控并发。
4. 回滚时停止使用新归因器并保留旧字段/键；新账本键自然过期，已有冷却键继续由兼容代码读取，不需要数据库迁移。
