# 说明
本提案将修复渠道监控失败请求未可靠将实际失败的 API Key 账号纳入冷却链的问题。

## Why

渠道监控页面显示失败时，当前冷却逻辑主要依赖网关转发错误，无法覆盖 HTTP 2xx 后由挑战校验、空响应或客户端超时导致的最终失败，也无法稳定保留换号过程中前序失败账号的归因。结果是账号仍可能被立即重复选中，冷却阶梯与监控结果不一致。

现在需要以监控最终 `CheckResult` 为统一判定，并记录一次模型监控请求实际尝试过的账号，保证失败归因完整且可审计。

## What Changes

- 为每个主模型或附加模型监控请求建立独立的 Redis 请求账本，关联监控请求标记、实际尝试过的账号及转发终态。
- 仅对实际尝试过且最终失败的普通 API Key 账号执行现有渠道监控冷却阶梯；OAuth、Setup Token、Service Account 和号池账号不纳入。
- 以最终 `CheckResult.status` 的 `failed` 或 `error` 作为唯一失败判定，覆盖网关 2xx 后的挑战失败、空响应、客户端超时等情况。
- 保留换号过程中前序失败账号的归因，即使后续账号成功，前序失败账号仍进入冷却链。
- 保持现有并发合并、冷却到期后的阶梯推进、成功清理连续失败计数且不缩短已生效冷却的规则，并通过幂等记录避免重复推进。
- Redis 不可用时，本次请求跳过全部冷却处理，不启用进程内兜底、不暂停监控、不阻塞原始请求，并记录错误日志或指标。
- 管理端账号列表和详情继续显示渠道监控冷却状态及原因，不新增管理配置项。

## Capabilities

### New Capabilities

- `channel-monitor-failure-cooldown`: 定义渠道监控请求的最终失败判定、账号尝试账本、API Key 冷却归因、故障降级和管理端状态投影。

### Modified Capabilities

无。当前仓库没有已注册的主规范能力；本次以独立能力规范建立完整契约。

## Impact

- 后端渠道监控服务、网关处理器及冷却服务/存储层需要协作传递请求标记、账号尝试记录和最终结果。
- Redis 数据结构和 Lua 原子操作需要增加请求账本及幂等终态记录；现有账号冷却键和冷却阶梯配置保持兼容。
- 管理端复用现有账号冷却状态接口和展示，需补充对渠道监控来源状态的回归验证。
- 不改变监控接口的外部请求格式、网关业务响应语义或系统设置页面。
